# Query Rewriting

## What it means

A user's latest message is often not a good standalone retrieval query.

Example conversation:

```text
User: Which pickup zones generate the most revenue?
Assistant: ...
User: what about airports?
```

The literal query:

```text
what about airports?
```

is weak for retrieval.

A conversation-aware rewrite might produce:

```text
Compare taxi revenue generated by airport pickup zones such as JFK and LaGuardia.
```

The rewrite is an internal representation used for retrieval/tool planning. It does not need to replace the user's original message or be shown as the answer.

## Current POC status

Query rewriting is **not explicitly implemented today**.

### `/api/ask`

The endpoint validates the prompt and forwards it unchanged:

```text
request.prompt
    ↓
orchestration_loop.run(request.prompt, conversation_id)
```

The HTTP endpoint should remain thin. Query rewriting is orchestration/query-understanding behavior, not transport behavior.

### `ContextReducer`

The reducer also does not rewrite the query.

More importantly, it currently runs after the MCP tool execution, so it is too late to improve the initial retrieval/tool-selection query.

### Proposal LLM

The proposal call currently receives:

```text
llm.propose_taxi_query(prompt, schema)
```

The model may infer intent and translate natural language into tool arguments. However, this is not an explicit reusable query-rewrite stage, and the rewritten interpretation is not separately observable, testable, or usable by another retriever.

## Recommended ownership

Do not put query rewriting in the `/api/ask` route.

Do not make it an incidental side effect of `ContextReducer`.

Introduce an orchestration-level query-understanding stage before retrieval/tool proposal.

Conceptually:

```text
/api/ask
   │
   │ original user message
   ▼
OrchestrationLoop
   │
   ├── load conversation state
   │
   ▼
QueryUnderstanding / QueryRewriter
   │
   ├── original_query
   ├── rewritten_query
   ├── inferred filters
   └── confidence / reason for rewrite
   │
   ▼
ContextRetriever
   │
   ▼
ContextReducer
   │
   ▼
Tool planning / LLM
```

For the current POC, retrieval may still be trivial. The important design point is where the stage belongs.

## Preserve both queries

Never discard the original user text.

A useful object is:

```text
ResolvedQuery
- original_query
- retrieval_query
- conversation_id
- inferred_entities
- inferred_filters
- rewrite_applied
```

Example:

```json
{
  "original_query": "what about airports?",
  "retrieval_query": "Compare taxi revenue for airport pickup zones, especially JFK and LaGuardia",
  "inferred_entities": ["JFK", "LaGuardia"],
  "inferred_filters": {"zone_type": "airport"},
  "rewrite_applied": true
}
```

The original query remains authoritative for user intent and auditability. The rewritten query is an optimization for downstream retrieval/planning.

## Rewriting should be conditional

Not every request needs another model call.

### Good candidates

```text
"what about airports?"
"and last Friday?"
"compare that to mornings"
"did it change?"
```

These contain references that depend on previous context.

### Usually unnecessary

```text
"Which pickup zones generate the most revenue?"
```

This is already a good standalone query.

A lightweight heuristic or the existing planning model can eventually decide whether resolution is necessary.

## Query rewrite vs tool planning

Keep these concepts distinct even if one model call eventually performs both.

```text
Query rewrite:
"what about airports?"
        ↓
"compare airport pickup-zone revenue"

Tool planning:
"compare airport pickup-zone revenue"
        ↓
query_taxi_data(...)
```

Query rewriting creates a better semantic request. Tool planning converts that request into an executable operation.

## Observability

If implemented, make rewriting visible in run telemetry/debug UI:

```text
query.received
query.rewrite.skipped
```

or:

```text
query.received
query.rewrite.started
query.rewrite.completed
context.retrieval.started
...
```

Useful metrics include:

- rewrite rate;
- rewrite latency;
- rewrite input/output tokens and cost;
- retrieval quality with/without rewriting;
- percentage of follow-up queries resolved successfully;
- fallback rate when rewrite confidence is low;
- missing expected rewrite/retrieval telemetry alerts.

The last item matters because absent instrumentation can otherwise look like a healthy zero-rate system.
