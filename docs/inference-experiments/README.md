This README explains how observability is set up on the cluster and how observations are captured. Everything below is read
from the repo as of 2026-10-04; the duplicate-scrape finding was confirmed live (`worker_warm` returned 4 series).

## The roles

- **Prometheus** stores numbers. Every 15s it pulls `/metrics` from the gateway, the workers and the GPU exporter, and it evaluates the alert rules against that history.
- **Grafana** draws charts. It stores nothing, and each panel is a Prometheus query.
- **Alerts** are Prometheus rules. They only change color in the `/alerts` page, because Alertmanager is off.

```
exporters (gateway, workers, DCGM, ...)  ◄── scrape every 15s ── Prometheus ◄── queries ── Grafana

                                                                                                from ConfigMaps
```

## When it is applied

Only by `make inference-deploy` (`infra/inference/scripts/deploy.sh`), which runs these steps over SSH on the instance, in order:

```
make inference-sync ─► inference-bootstrap ─► inference-config ─► inference-deploy
 (rsync repo)           (k3s, helm, HAMi)      (namespace+cm)            │
                                                                         ▼
  ┌─ 1 apply k8s/ (gateway, workers, services, HAMi slices)
  ├─ 2 apply DCGM exporter
  ├─ 3 build temp values file ◄── alerts.yaml nested under serverFiles
  ├─ 4 helm upgrade --install prometheus ◄── values.yaml + temp alerts values
  ├─ 5 helm upgrade --install grafana    ◄── grafana/values.yaml
  ├─ 6 ConfigMap inference-dashboards    ◄── grafana/dashboards/*.json
  ├─ 7 ConfigMap inference-gateway-code  ◄── gateway/
  └─ 8 wait for rollouts ─► print Grafana password
```

Steps, in words:

1. `kubectl apply` the namespace and everything under `k8s/` (gateway, workers, services, HAMi slices ConfigMap).
2. `kubectl apply` the DCGM exporter.
3. Build a temp values file that nests `alerts.yaml` under `serverFiles: / alerting_rules.yml:`.
4. `helm upgrade --install prometheus ... -f values.yaml -f <temp alerts values>`.
5. `helm upgrade --install grafana ... -f grafana/values.yaml`.
6. Create ConfigMap `inference-dashboards` from `grafana/dashboards/` and label it `grafana_dashboard=1`.
7. Create ConfigMap `inference-gateway-code` from `gateway/` (the gateway pod mounts its code from it).
8. Wait for rollouts (workers up to 15 min each), then print the Grafana admin password.

It is idempotent. Re-run it after changing `values.yaml`, `alerts.yaml`, dashboards or manifests. Deploy resets gateway env to
the manifest defaults (experiment controls OFF). A gateway-code-only change needs only `make inference-gateway-restart`.
`inference-sync` (rsync of the repo to the instance) must come first, because every path in deploy.sh is on the remote copy.

## What `prometheus/values.yaml` does

- `server`: no persistent volume, ClusterIP service, scrape and evaluation interval 15s.
- `extraScrapeConfigs`: four explicit static jobs.
  - `inference-workers`: worker A/B services, port 8000 (vLLM metrics).
  - `inference-gateway`: gateway service, port 8080, `/metrics`.
  - `hami`: HAMi device-plugin monitor (31992) and scheduler (31993) in `kube-system`.
  - `dcgm`: the DCGM exporter, port 9400.
- Subcharts: kube-state-metrics and node-exporter on; alertmanager and pushgateway off.

## Alerts

`alerts.yaml` has 5 rules (the plan said 4; the fifth is `InferenceEngineTTFTHigh`). Visible at Prometheus `/alerts`
(`http://127.0.0.1:19090/alerts` through the tunnel).

## Grafana

Grafana's sidecar watches ConfigMaps in all namespaces for the label `grafana_dashboard=1` and loads them as dashboards.
The Prometheus datasource (uid `prometheus`) is provisioned to `prometheus-server.inference-lab.svc.cluster.local:80`.

## Known issue: gateway and workers are scraped twice

```
 gateway pod ──annotation prometheus.io/scrape ──► job="kubernetes-pods"   ─┐
      │                                                                     ├─► 2 series per metric
      └──── static job in values.yaml ────────────► job="inference-gateway" ─┘
 (workers: same pattern with job="inference-workers")
```

The pods carry `prometheus.io/scrape: "true"` annotations (port 8080 for the gateway, 8000 for the workers). The chart's
default `kubernetes-pods` job discovers them, while `values.yaml` also scrapes them as static jobs. Each metric therefore has
two series, `job="kubernetes-pods"` and `job="inference-gateway"` (or `inference-workers`). Effects: dashboard legends repeat
(`worker_a, worker_b, worker_a, worker_b`), and any unfiltered `sum`/`count`/`rate` double-counts. Workaround: filter
`{job="inference-gateway"}` or `{job="inference-workers"}`. Fix (parked, not applied): remove the annotations from the three
manifests, or drop the explicit jobs. Only the gateway duplicate is confirmed live; the worker duplicate is inferred from the
annotations.

# Methodology: how we capture observations

Sources: `docs/inference-experiments/inference-run-playbook.md`, `Makefile` targets, `infra/inference/scripts/pull-evidence.sh`. No real run had produced these artifacts when this was written, so file names are what the tooling is documented to write.
### Principle

Run one controlled change at a time (control vs treatment), and record evidence at **two scopes**. Never mix them.

| Scope | Where it comes from | What it can claim |
|---|---|---|
| **Per-request** | the replayer's `requests.jsonl` (client-side: TTFT, latency, status, placement) | what each request experienced |
| **Window-level** | Prometheus deltas and range series over the run window | what the system did during that window (GPU, KV cache, queues, sheds) |

A window delta must never be attributed to a single request. `--metrics-url` scrapes one worker only, so for the
two-worker picture use the Prometheus range export. Run nothing else during a measured run, and never overlap runs.

### The capture loop

```
 1 pre-flight          2 set up the run         3 run the replayer            4 capture            5 analyze
 ┌─────────────┐      ┌───────────────────┐    ┌───────────────────────┐    ┌───────────────┐   ┌──────────────────┐
 │ health,     │      │ RUN_ID=d123-<D>-eN │    │ make replay-*         │    │ pull-range    │   │ evidence-analyze │
 │ worker_warm,│ ───► │ export manifest    │ ─► │ (or run_scenario,     │ ─► │ pull-evidence │ ─►│ notebook         │
 │ dashboards, │      │ inputs, controls   │    │ warmup, capacity)     │    │ gateway log   │   │ trace-request    │
 │ alerts      │      │ restart workers if │    │ writes requests.jsonl │    │               │   │                  │
 └─────────────┘      │ the cache matters  │    │ summary, manifest     │    └───────────────┘   └──────────────────┘
                      └───────────────────┘    └───────────────────────┘
        Grafana + Prometheus /alerts are watched live during step 3 (not a record, a sanity check)
```

### What each step records

1. **Run id and directory.** `RUN_ID=d123-<YYYYMMDD>-<experiment>`; everything lands in `metrics/inference/$RUN_ID/`
   (gitignored).
2. **Manifest inputs** (exported before the run, reused for every run in a comparison): `MODEL_REVISION`,
   `TOKENIZER_REVISION`, `CHAT_TEMPLATE_REVISION`, `ENGINE_FLAGS`, `VLLM_VERSION`, `KV_BLOCK_SIZE`,
   `INFERENCE_TOPOLOGY`, optional SLO overrides. Unset ones are stored as `unknown`, and then a match between two runs
   cannot be proven.
3. **Replayer output** per run directory `<scenario>_<strategy>_<timestamp>/`: `requests.jsonl` (per request),
   `summary.json` (per level, plus `prometheus_window`), `sweep.json`/`sweep.csv`, `manifest.json` (scenario hash, policy,
   SLOs, prefix size, controls requested vs verified).
4. **Cluster capture.**
   - `make inference-pull-range RUN_ID=<id> [START END STEP]`: Prometheus range series written to
     `prometheus_range/<query>.json`. Queries are listed in `observability/prometheus/evidence_queries.json`: HBM used/free
     (DCGM), KV usage, running/waiting requests, request rate, preemptions, prefix hit ratio, TTFT/queue quantiles, gateway
     queue depth/sheds/picks. Needs the tunnel.
   - `make inference-pull-evidence RUN_ID=<id>`: pods/deployments/services as JSON, worker and DCGM logs, `nvidia-smi`
     snapshots, and a raw `/metrics` scrape of each worker.
   - Gateway log (for single-request traces): `kubectl logs deploy/inference-gateway` saved by hand.
5. **Analysis.** `make evidence-analyze RUN=... RANGE=...` prints a text summary and the control-vs-treatment verdict
   (`comparable: true/false` with reasons). `make evidence-notebook` fills `experiments/123_evidence.ipynb`.
   `make trace-request` explains one request end to end.

### Rules that keep the comparison honest

- **Control vs treatment** differ in exactly one thing. The manifest check reports `comparable: false` otherwise.
- **Same cache state:** restart workers before each run when cache matters (E1, E2, E3).
- **Controls are verified**, not assumed: the replayer exits immediately if the gateway does not echo the policy control.
- **Honest labels:** E2 is "first pass vs fully warm", not "no cache vs cache". Report negative or neutral results as found.
- **Dashboards are for watching, files are for evidence.** Grafana and `/alerts` show a run live; the claims in the
  presentation come from the pulled files.

### Where Grafana, Prometheus and alerts fit

Prometheus is both the live monitor and the source of the window-level series (`pull-range` queries its HTTP API).
Grafana only displays it. Alerts (5 rules, Prometheus `/alerts`) are a live signal, for example SLO breach or queue/shed
surge, and you should record which ones fired during E4. The replayer's files remain the per-request record.

### Open caveats

- The gateway is scraped by two jobs (see "Known issue: gateway and workers are scraped twice" above), so unfiltered Prometheus sums can double-count. Filter
  by `job` for any number you present, and check the evidence queries for the same issue (not checked).
- Live Grafana rendering and the `promtool` check were listed as unverified before this session; only some panels have been
  seen here.
